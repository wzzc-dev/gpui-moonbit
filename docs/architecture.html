gpui-moonbit アーキテクチャ

Zed の GPUI（Rust 製 GPU アクセラレーション UI）を、C ABI を介して MoonBit から駆動する実験的ブリッジ。
MoonBit が main を所有し、Rust は実行ファイルにリンクされる静的ライブラリとして動く。

1. 全体像 — 何がどこにあるか

登場人物は 3 つだけ。MoonBit 側（UI の記述とアプリの状態）、C ABI 境界（両者の唯一の接点）、Rust 側（ツリーの保存・GPUI へのレンダリング・イベント配線）。 関係は 双方向で、行きは「コマンドバッファ 1 回の FFI 呼び出し」、帰りは「5 個の i32 だけを運ぶコールバック」という非対称な形をしている。

MoonBit が持つもの

  • main エントリポイント（moon run で起動）
  • アプリの状態とイベントの意味づけ（消費者アプリ。例: examples/counter）
  • UI ツリーの記述と CommandBuffer のエンコード

Rust が持つもの

  • コミット済みノードツリー VIEWS（唯一の真実）
  • GPUI 要素へのレンダリングとイベントリスナー
  • スクロール位置などメインスレッド専用の状態

3. 実行時モデル — retained + reactive

仮想 DOM の差分計算は意図的に持たない。MoonBit がツリー全体を記述して送り、Rust がそれを保存し、GPUI が描く。状態が変わったらもう一度送り直す、というシンプルな契約になっている。

1 回の更新で起きること

  • MoonBit がイベントを受け取り、状態（count）を変更する
  • まず その場更新を試す — update_text(view, COUNT_KEY, …) でキー付き div の最初のテキスト子だけを書き換える
  • キーが見つからなければ（KEY_NOT_FOUND）フルリビルドにフォールバック — 新しいコマンドバッファでツリーをゼロから作り直して build_tree
  • MoonBit が 1 を返す → Rust が cx.notify() → FfiView::render が再実行される
  • 何も変化しないイベントは 0 を返し、再構築も再描画も起こらない

コマンドバッファはスタックマシン

プロパティごとに FFI を呼ぶのではなく、全ノードの記述を 1 本の length-delimited なオペコード列にまとめ、FFI 呼び出し 1 回で渡す。

  • ノード生成（OP_DIV / OP_TEXT）がハンドルを内部スタックに push する
  • セッター（OP_SET_*）はスタックトップに適用される
  • OP_ADD_CHILD は child → parent の順に pop し、parent を push し直す
  • OP_SET_ROOT がトップを pop してルートにする

Rust 側はまずステージングツリーを組み、ルートの存在とキーの重複を検証してから、成功したときだけ VIEWS[view] を差し替える。失敗すれば以前のツリーは無傷のまま。ヘッダは "GPUI" マジック + BUFFER_VERSION で始まる。

オペコードの追加は後方互換。 古い Rust バイナリは知らないオペコードを UNKNOWN_OPCODE で拒否するだけで、誤ってデコードすることはない。だから BUFFER_VERSION を上げるのは「既存オペコードの意味が変わったとき」だけでよい。

条件GPUI ElementId再構築を跨いだ安定性

4. FFI 契約 — 行きと帰りで形が違う

行き: MoonBit → Rust（C ABI）

C シンボル役割
gpui_build_treeコマンドバッファ 1 回でツリーを構築・コミット
gpui_run_windowウィンドウを開き GPUI ループでブロック
gpui_update_textキー付き div のテキストをその場更新
gpui_event_copy_textEVENT_TEXT のペイロードを同期コピー
gpui_debug_dump_textツリーのテキストを DFS で読み戻す
gpui_abi_probeInt == i32 の境界往復検証

帰り: Rust → MoonBit（コールバック）

コールバックはたった 1 つ。ライブラリ所有の dispatch_entry(version, kind, view, data_a, data_b) -> Int を、Rust がマングル名経由で直接呼ぶ。dispatch_entry は純粋な委譲で、消費者が register_dispatch で登録したクロージャをそのまま呼ぶ（RFC 0004）。

slot中身
0ABI_VERSION（= 4）。不一致なら MoonBit が Unknown を返して拒否
1イベント種別 CLICK=1 / KEY=2 / TEXT=3 / NAMED_KEY=4 / ASYNC=5 / INPUT_CHANGED=6 / INPUT_SUBMIT=7 / SCROLL=8
2view id（VIEWS のインデックス）
3, 4data_a / data_b（click_id, コードポイント, token, 修飾キー, input_id, scroll_id…）
なぜ 5 個の i32 だけなのか。 MoonBit native は非アトミックな参照カウントで動くランタイムなので、ヒープオブジェクトを境界を跨いで持ち回れない。64 ビットポインタも i32 スロットに収まらない。だからテキストのような可変長ペイロードは Rust 所有のキューに置き、token だけを渡して gpui_event_copy_text で同期的にコピーさせる方式になっている。

なぜ素の cargo build / moon build ではダメなのか

  • 素の cargo build には、ローカル生成される mb_symbol.txt が無い（＝コールバックの extern を出せない）
  • 素の moon build は、MoonBit が外部静的アーカイブの変更を追跡しないため古い実行ファイルを残すことがある
  • だから必ずルートの build.sh / build.ps1 を使う。ドライバは前提チェック → 生成 → ビルド → リンケージ検証（コールバック定義がちょうど 1 つ）→ 往復テスト、まで一気にやる
bindgen は 1 つ前のヘッダを見る。 パイプライン上、bindgen-moonbit が走るのは cargo がヘッダを再生成する前。したがって Rust の C エクスポートを変えた直後は、ドライバをもう一度走らせて、再生成されたヘッダと追跡対象の gpui-bindings-ffi.mbt を同期させる必要がある。

6. MoonBit native ならではの制約

API が強制してくれないので、呼ぶ側が守る必要があるルール。ここを外すと静かに壊れる。

  • コールバックはメインスレッド限定。 ランタイムの参照カウントは非アトミック（int32_t rc）。別スレッドから dispatch_entry を呼ぶとデータ競合になる。register_dispatch も同じ制約（run_window より前・メインスレッド）
  • コールバックは素のトップレベル関数。 MoonBit のクロージャは「コードポインタ + 環境」の RC ヒープオブジェクトで、C の関数ポインタとしてエクスポートできない。だから「Rust からマングル名を直参照して呼ぶ」の一択
  • envelope はスカラのみ。 MoonBit のヒープオブジェクトを Rust 側に保持してはいけない（incref/decref を避けるため）
  • MoonBit Int == Rust i32。 前提ではなく、gpui_abi_probe が毎ビルド i32::MAX / i32::MIN / 0 / -1 の往復で機械検証している
  • panic はプロセス abort。 MoonBit の例外は FFI 境界を越えられない。Rust 側は catch_unwind で捕捉して INTERNAL_PANIC を返し、境界の外へ漏らさない
